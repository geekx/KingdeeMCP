# 金蝶对象操作

**以对象为中心,不是以工具为中心。** 不要先想"该调哪个工具",
先打开对象,系统会告诉你此刻能做什么。

底座只有 10 个工具,对象类型(84 个)和它们的动作、链接全部按需查,不常驻上下文。
所以第一步永远是打开对象,不要凭记忆猜 form_id——各家二开不同,记忆一定过期。

## 主循环:打开 → 看能做什么 → 做

```
kd_object(noun="采购订单", id="CGDD000231")
```

一次返回四样东西:

| 字段 | 是什么 |
|---|---|
| `properties` | 属性及其当前值 |
| `state` / `state_zh` | 当前状态(从属性反推的规范码,如 `C:已审核`) |
| `actions` | **此刻**能做哪些动作,不能做的带 `reason` |
| `links` | 它连到哪些对象,方向是 outgoing(能推出)还是 incoming(由谁推来) |

然后照着 `actions` 里 `enabled=true` 的动词调 `kd_act`。

### 关键:不要自己判断能不能做

`actions[].enabled` 已经把状态前置条件算过了。看到 `enabled=false` 就读 `reason`,
它会说清"要求什么状态、当前是什么"。**不要绕过它硬发请求**——
那只会换来服务端一个更难懂的报错。

`unverified: true` 表示状态没取到,可用性未经核实。此时可以试,但要预期可能被拒。

## 只有一个单号,不知道是什么单

```
kd_object(identify="CGDD000231")
```

按编号前缀推断,返回**候选 + 依据**,不是断言——前缀由租户的编码规则决定
(见对象 `SYS_NumberRule`),各家不同。命中只说明"很可能是",拿候选去
`kd_object(noun=候选, id=编号)` 查一下就确认了。认不出也很正常,
这时候直接问用户是什么单,别硬猜。

## 不知道对象叫什么时

```
kd_object(search="采购")              按关键字搜类型
kd_object(category="bill")            按类别列:bill/master_data/view/system
kd_object(noun="采购订单")             类型卡片:这类对象长什么样、能做什么
```

类型卡片和实例卡片**同形状**,只是没有实例数据——不必学两套结构。

## 先看有没有现成的流程

对象卡片里的 `operations` 是**本租户已经编排好的业务操作**。
有现成的就别自己拼步骤——`starts_here: true` 表示这个操作正是从当前对象起步。

```
kd_run(operation="销售开票", targets=["XSDD001"])
```

## 动作:先看契约再决定怎么重试

`kd_act` 的返回体一定带 `contract`。**失败后先读它再决定动作**:

| `atomicity` | 失败后怎么办 |
|---|---|
| `per_item` | 部分成功。只重试 `failed` 里的目标,别整批重发——已成功的不会回滚 |
| `server_defined` | **无法知道哪些已生效**。必须 `kd_query` 逐个查证后再重试 |
| `atomic` | 系统状态未变,改了直接重试 |

还有两个字段决定要不要先问人:

- `destructive: true`(无逆动词)——**执行前必须让用户明确点头**,即使用户在催
- `inverse: "unaudit"`——做错了可以用这个动词退回

### 执行前先看 advisories(有才会带)

`kd_act` 判断层的忠告,不阻断,但**要念给用户听、别静默略过**:

| 规则 | 什么时候出现 | 该做什么 |
|---|---|---|
| `AIP-04` | 动作不可逆(`destructive`) | 执行前让用户点头;`fix` 里会说清有没有补偿动作可用 |
| `AIP-05` | 动词走金蝶「操作」接口(close/void/forbid/…)且未给 `operation` | 提醒会用默认操作编码——二开单报错常出在这,提前说比事后翻日志省事 |

没有忠告时这个字段根本不存在,不必判断是不是空数组。

## 导航到下游单据

```
kd_object(noun="采购订单", id="CGDD000231", navigate_to="采购入库单")
```

下游单据引用源单的字段名(`FSrcBillNo` / `FSourceBillNo` / …)随表单和二开而异,
静态推断不出唯一答案,所以系统会**逐个候选替你试**,命中即返回结果并说明是哪个字段生效。

看返回里的这两个字段:

- `confirmed_by_probe: true` —— 探测命中。**这是试出来的,不是账套确认的**,
  结果可信但字段名值得人眼核对一下;
- `confirmed_by_probe: false` —— 都没查到。有两种可能:确实还没下推,
  或本账套用了别的关联字段。别只报第一种。

命中后系统会往知识库提一条"把 `link_filter` 写进 profile"的建议
(只提议,不自动改配置)。**顺口告诉用户这件事**——试出来的答案不该下次再试一遍。

## 新建单据

```
kd_describe(what="template", key="销售订单")     取已验证的骨架
kd_act(verb="save", noun="销售订单", model={...}, dry_run=True)   先校验不写入
kd_act(verb="save", noun="销售订单", model={...})                 确认无误再存
```

`dry_run` 只对 `save` 有效——其它动词没有预演接口。

## 多步业务操作 = 多扣扳机组(Saga)

租户可能已经把常做的事定义成入口。这不是"顺序打一串动作"——
像 12306 那条链(查询 → 付款状态 → 扣库存 → 出单),关键是**每步有守卫、
有些步要人单独点头、失败要把已生效的按逆序退掉**。

```
kd_describe(what="operations")
kd_run(operation="销售开票", targets=["XSDD001"])
```

**未确认时不做任何写操作**,只返回执行计划。把计划念给用户听,
得到同意后带 `confirmed=True` 重跑。

### 看 `state`,别看有没有报错

| `state` | 含义 | 你该做什么 |
|---|---|---|
| `awaiting_auth` | 停在某一步等人授权 | 把 `awaiting` 里的内容念给用户,拿到姓名后授权 |
| `done` | 全部完成 | — |
| `compensated` | 失败了,但已按逆序退干净 | 告知用户,没有遗留 |
| `halted` | 停了,**且有东西没退掉** | 念 `left_behind`,帮用户决定续做还是清理 |
| `compensation_failed` | **最坏**:试图收拾但没收拾干净 | 立刻告诉用户 `left_behind` 必须人工处理 |

### 逐步授权

**整体确认一次 ≠ 全权委托。** 标了『授权』的子任务会各自停下来:

```
kd_saga(action="authorize", run_id="…", by="李主管")          批准
kd_saga(action="authorize", run_id="…", by="李主管", approve=False, reason="金额不对")
kd_run(operation="销售开票", run_id="…", confirmed=True)       批准后继续跑
```

**授权必须记名**——`by` 不能空,谁批的要能查到。
授权前先把 `awaiting.describe` 和「这一步能不能补偿」念给用户:
`compensable: false` 意味着做了就退不回来,这个必须说。

### 定期清一下没了结的

```
kd_saga(action="list")
```

**等授权的运行最容易被忘掉**——放着不管,已生效的写操作就成了无人认领的中间态。

## 排查"这单怎么卡住了"

```
kd_audit(scope="dangling")
```

列出未清算的中间态:写操作已生效、整条链没走完、也没有补偿记录的单据。

## 排查"连不上/一查就报错"

第一次接入,或者查询/写入总是失败,先确认是不是配置或权限本身的问题,
别急着当成业务问题排查:

```
kd_check_profile(probe=True)
```

真登录一次、只读探测几类常见单据,报告账号密码对不对、这个账号大概能碰到
哪些模块。**会真的向账套发请求**,只读,不碰任何写动词。

## 五条硬规矩

1. **不要凭记忆猜 form_id 或下推关系**,一律先 `kd_object`。
2. **`destructive` 的动作执行前必须让用户确认**,即使用户催。
3. **`outcome: "unknown"` 不等于失败**——服务端可能已生效。重试前先查证,否则会重复建单。
4. **部分成功时不要整批重发**,只针对 `failed`。
5. **缺某个对象类型或下推关系时不要绕过校验**,告诉用户去
   `profiles/<租户>/profile.yml` 补一行(业务人员可自行填写,见 `profiles/README.md`)。
