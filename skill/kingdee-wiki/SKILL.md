# 每日回溯与自优化

## 什么时候用

- 用户说「做个复盘/回顾/回溯」「最近怎么样」
- 用户问「哪些操作老失败」「有没有卡住的单」「该改哪里」
- 定时任务里每天跑一次

## 怎么跑

```bash
python3 -m wikiskill.retro                    # 昨天+今天，写入知识库
python3 -m wikiskill.retro --day 2026-09-02   # 指定日期
python3 -m wikiskill.retro --all              # 全部历史
python3 -m wikiskill.retro --report           # 只看，不写入
```

输出分两部分：本次扫描统计（新增/强化/已否决跳过），以及**可执行项**。

## 关键：没有可执行项是正常的

只出现一两次的观察是噪声，会先攒证据不打扰人。
跨天反复出现才升到 `medium` 浮上来。**不要因为今天没有可执行项就去翻原始日志找茬** ——
噪声抑制是设计意图，不是功能缺失。

置信度 = 出现次数 × 覆盖天数：

| 置信度 | 门槛 |
|---|---|
| `noise` | 攒证据中 |
| `low` | ≥2 次 |
| `medium` | ≥5 次且跨 ≥2 天 —— **值得动手** |
| `high` | ≥10 次且跨 ≥3 天 |

## 汇报给用户时

按置信度从高到低讲，每条说清三件事：**现象、证据量、建议动作**。
建议里已经指明了改哪个文件的哪一段，照实转述，不要泛泛说"建议优化"。

区分这几类的处置方向：

| 类型 | 通常该改哪里 |
|---|---|
| `failure_pattern` | 错误模式库 / 字段模板 / 前置状态声明 |
| `dangling` | 先人工清理 `left_objects`，再考虑加确认或补偿 |
| `flaky` | 排查超时；长期给 save/push 加幂等键 |
| `unlinked_push` | 让业务同事补 `profiles/<租户>/profile.yml` 的 `links` |
| `slow` | 收窄字段集、减小批量 |

## 处置

**只提议，不自动改。** 自动改 ERP 的操作定义是危险的。落地要人点头：

```bash
python3 -m wikiskill.retro --adopt <id>
python3 -m wikiskill.retro --reject <id> --note "业务上就是这样，不改"
```

被 reject 的条目**不会复活**：计数继续累积，但不再出现在可执行项里。
所以当用户说「这条不用管」时，务必真的执行 `--reject` 并记下理由，
否则明天同样的建议会再提一遍。

## 顺带查中间态

回溯里的 `dangling` 条目对应的是**未清算的中间态**：写操作已生效、
整条链没走完、也没有补偿记录的单据。要看实时状态用底座工具：

```
kd_audit(scope="dangling")
kd_audit(scope="trace", trace_id="...")     # 某次操作的完整步骤
```

这些单据不会自动回滚，需要人决定继续走完还是清理掉。
